# L-9 — Panel CORS defaults to localhost-only; Secure cookies break plain-HTTP LAN hosts

**Status:** Fixed (2026-10-30 — `cors` plugin now supports `CORS_ALLOW_ORIGINS=*`)
**Group:** 7. Lower-severity / operational findings

**Location:** `apps/api/src/plugins/cors.ts`, `apps/api/src/config.ts`.  
**What was wrong:** The API only served CORS headers for origins listed in
`CORS_ALLOW_ORIGINS`, which defaulted to
`http://localhost:5173,http://localhost:5174`. A panel served from a machine's
LAN IP (e.g. `http://10.1.206.54:5174`) failed the preflight with
`No 'Access-Control-Allow-Origin' header is present`, so login was blocked even
though the API was reachable. Separately, on plain-HTTP hosts `cookieSecure`
defaults to `true` under `NODE_ENV=production`, so the browser rejected the
session cookie and login never stuck even after CORS was fixed.  
**Fix:** The plugin now treats `"*"` in `CORS_ALLOW_ORIGINS` as "reflect any
Origin header with credentials" (the spec forbids `*` + credentials, so the
request origin is echoed) — one deployment works from any panel origin
(localhost, LAN IP, hostname, any port) without enumerating machines. The
explicit allow-list still works as before; `config.ts` parses/dedupes the list.
For plain-HTTP hosts set `COOKIE_SECURE=false` (as `ops/.env.docker` now does
for the sandbox stack); keep it `true` once TLS is used.  
**Suggested fix (operator):** set `CORS_ALLOW_ORIGINS=*` (or a fixed list
including every panel origin) and `COOKIE_SECURE=false` when not using TLS;
point `VITE_ADMIN_API_BASE_URL`/`VITE_API_BASE_URL` at the API's host and run
Vite with `--host`.  
**Verification:** `cors.test.ts` now covers preflight + simple requests against
a wildcard config using a LAN origin (`http://10.1.206.54:5174`) and asserts
the reflected header + credentials; the origin-less and disallowed-origin
cases still return no CORS headers.  
**Confidence:** High — reproduced live before the fix.
